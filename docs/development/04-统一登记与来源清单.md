## 2. 原理与数据分工

### 2.1 SHA-256 标识什么

SHA-256 将文件字节映射为 64 位小写十六进制字符串。改文件名不改变哈希；修改 PDF 元数据或正文可能改变哈希。这里用它识别字节相同的文件，不能据此判断两个不同 PDF 是否属于同一篇论文，也不能证明内容或来源可靠。

实现使用 Python 标准库 `hashlib.sha256()`，每次读取 1 MiB，内存不随 PDF 总大小增长。只读取待登记文件；与既有论文比较时使用清单中已保存的哈希，不重读已登记语料。因此手工修改已登记 PDF 会破坏清单与文件的一致性，日常登记不会替你发现这种修改。

### 2.2 为什么保留两个文件

|文件|职责|使用方|
|---|---|---|
|`configs/pdf_files.json`|轻量 ID → 相对于 raw 的文件路径|现有 PDF 解析脚本|
|`data/source_manifest.jsonl`|每行一篇文档的哈希、路径、状态和来源元数据|来源核对与后续文档管理|

两者用 `doc_id` 关联，不将作者、DOI 等字段塞进路径配置。JSONL 每行是一条完整 JSON 对象，不加行间逗号，也不在外层套数组。默认新增批次会保留旧记录的全部字段值并追加记录；显式 `--refresh-metadata` 可更新旧记录的指定字段；文件按 ID 排序重写，缩进、行序等格式不承诺原样保留。默认没有新 PDF 时不重写；显式刷新且旧记录有变化时只更新来源清单。

### 2.3 路径基准

路径配置中的 `registered/Example.pdf` 相对于 `data/raw/`。

来源清单中的 `raw/registered/Example.pdf` 相对于**来源清单所在目录**，默认就是 `data/`。因此两个字符串不同，但指向同一份文件。切换终端当前目录不会改变其含义。自定义 raw 根目录时，来源清单必须与它同级，以便保持这个约定；例如 `/tmp/trial/papers/` 对应 `/tmp/trial/source_manifest.jsonl`，记录保存 `papers/registered/...`。

原设计示意中的 `data/raw/...` 已改成上述清单相对路径；不要将这两种基准混用。当前清单遵循该路径基准，元数据刷新不会改变路径。

## 5. 关键实现拆解

### 5.1 先验证旧产物

路径配置继续检查重复 JSON 键、非法 ID、大小写冲突和不安全的相对路径。来源清单逐行解析，拒绝重复键、重复 ID、无效哈希、重复哈希、与配置不一致的 ID 和路径。校验不要求作者等人工字段已经填好，不会覆盖用户已核实的字段。

配置与来源清单任一缺失时，只有另一份也是空数据才可能继续；已有非空数据不允许失配。这样不会在删除配置后误丢失已收录论文记录。脚本不联网推断来源网站信息；文件名元数据刷新是第 5.5 节的显式操作。

### 5.2 对待登记文件计算哈希

保留原来的 ID 和目标路径校验，再调用 `sha256_file()`。哈希表起初包含旧清单的哈希，每加入本批一篇就补入其哈希；后续发现同值就整批报错。这既覆盖“新文件与旧记录重复”，也覆盖“同批两个不同名字内容相同”。

此阶段仅构造内存计划；即使末尾一个文件重复，前面的文件也尚未移动。`.pdf` 扩展名检查不验证内部格式，测试用占位字节只是为了验证登记规则。

### 5.3 创建待核对的来源记录

登记时将 `language` 统一设置为 `en`。规范文件名按 `渠道-四位年份-完整标题.pdf` 拆分：例如 `CIKM-2023-STAEformer-A Spatial-Temporal Model.pdf` 对应标题 `STAEformer-A Spatial-Temporal Model`、年份整数 `2023`、渠道 `CIKM`。先去除文件名中连字符两侧空白，再拆出渠道、年份和标题；其他单词间空格和大小写保留。显示标题属于元数据，已填写的标题不随已登记文件名迁移而改写。

`arXiv-2020-...` 的渠道保存为 `arXiv`，年份沿用文件名的首次提交年，不伪装成会议发表年；`Unknown` 渠道或年份转为 `null`。不符合格式时标题保留整个文件名去扩展名、年份和渠道为空。文件名只是当前命名信息，后续 PDF 解析发现差异时可修正元数据，ID 保持不变。

作者、DOI、预印本 ID、版本等先保持空值，等 PDF 解析后再填写。`source_url` 和 `attachment_url` 暂为 `null`，当前无须查询网站；`published_at` 为空，不根据年份拼造日期。记录不再生成 `downloaded_at` 和 `notes`。

### 5.4 移动后复核与提交

执行前比较配置和来源清单原字节，任一变化就退出。PDF 继续使用原有硬链接加删除源路径的方式移动，不覆盖目标；要求源与目标在同一文件系统并支持硬链接。

全部移动后重新计算目标文件的哈希，与计划值比较，避免把预检后变化的 PDF 配上旧哈希。不一致时恢复本批文件，用户可检查后重新运行。

配置和来源清单分别使用同目录临时文件写完后替换。第二份写入失败时也会尝试恢复第一份原字节，再将 PDF 反向移回；首次登记没有旧产物时，移除本次创建的产物。恢复失败会在异常中列出路径，不假装已经回滚成功。

两个替换操作不构成数据库事务。没有并发锁，也不保证强制终止、断电或并发编辑时自动恢复；普通异常恢复与强制中断的处理方式见第 9 节。

### 5.5 刷新已登记记录

普通登记继续保持旧记录不变，避免无意改写人工补充信息。显式 `--refresh-metadata` 则对内存中的旧记录执行以下规则：

1. 设置 `language=en`；不新增 `lan` 字段，沿用统一字段名 `language`。
2. 标题为空或仍等于完整 `doc_id` 时，用文件名解析出的纯标题替换。
3. `metadata.year` 和 `metadata.venue` 仅在缺失或为 `null` 时补齐，已填写的值保留。
4. 移除 `downloaded_at` 和 `notes`，其余字段包括人工补充的作者、DOI、状态和自定义字段保持原值。

计划会统计真正发生变化的旧记录数，`--dry-run` 只显示统计，不写入。只有元数据变化而无新 PDF 时，不读取或移动已登记 PDF，不重算哈希，不重写路径配置，只原子替换来源清单；写入失败恢复清单原字节。重复刷新没有变化时不写入。

该选项仍会正常处理待登记目录中的新 PDF，所以对当前仅刷新旧记录的场景，应保持 `unregistered/` 为空。开发测试覆盖刷新与正常追加共用的计划和提交流程。

## 6. 输入输出示例和参数

以下是**格式示意**，不是正式论文或实际哈希结果。输入文件 `data/raw/unregistered/CIKM-2023-ExamplePaper.pdf` 在登记后对应：

`configs/pdf_files.json`：

```json
{
  "CIKM-2023-ExamplePaper": "registered/CIKM-2023-ExamplePaper.pdf"

```

`data/source_manifest.jsonl` 中的一行，哈希占位符由脚本实际计算的 64 位值替换：

```jsonl
{"doc_id":"CIKM-2023-ExamplePaper","title":"ExamplePaper","doc_type":"research_paper","language":"en","source_url":null,"attachment_url":null,"published_at":null,"raw_path":"raw/registered/CIKM-2023-ExamplePaper.pdf","sha256":"〔脚本实际计算的 SHA-256〕","status":"downloaded","related_doc_ids":[],"metadata":{"authors":[],"year":2023,"venue":"CIKM","doi":null,"arxiv_id":null,"version":null,"paper_role":null,"research_topic":null}}
```

该占位哈希不能作为真实输入通过校验。未知标量为 `null`，作者及关联 ID 为列表；人工补充时保持 JSON 数据类型，年份用整数，作者用字符串列表。

|参数|默认与作用|
|---|---|
|`--raw-dir`|项目 `data/raw/`；扫描内部 `unregistered/`，移入内部 `registered/`|
|`--config`|项目 `configs/pdf_files.json`；不能位于 raw 内或是符号链接|
|`--manifest`|raw 父目录下 `source_manifest.jsonl`；可改文件名，必须与 raw 同级，不能与配置同路径或是符号链接|
|`--dry-run`|读取新 PDF、计算哈希并展示计划，不创建目录、不移动、不写入|
|`--refresh-metadata`|刷新已有记录的英文及文件名字段，移除两个不再使用的字段；可与预览组合|

显式相对参数按终端当前目录解析，默认项目参数按脚本所在项目解析。隔离试验至少同时指定 `--raw-dir` 与 `--config`，来源清单默认跟随临时 raw，避免写入正式配置。

## 7. 用户正式运行与验收

### 7.1 先预览，再执行

**操作位置：服务器终端，项目根目录，已激活 `fiona`。**

```bash
python scripts/update_pdf_files.py --dry-run
python scripts/update_pdf_files.py
```

先看完第一条的冲突提示、计划移动路径和 SHA-256，再运行第二条。首批 44 份尚未登记且没有冲突时，预期显示“待登记 44 份 PDF，配置共 44 项”；本批现在已经登记，再运行普通登记预期为 0 份待登记、配置共 44 项。这是命令输出的解读示例，不是开发者重新执行正式登记的结果。

正式执行会移动本批文件，并替换或创建两份产物；后续新增批次会保留旧映射、旧元数据，追加新记录。`unregistered/` 始终保留；未使用刷新选项且无新 PDF 时正常退出，不改写产物。成功退出码为 0；路径、重复内容、配置或写入错误退出码为 2。

预览和正式执行是两次独立规划，会各自读取待登记 PDF；正式执行还会在移动后复核一次哈希。文件越大，读取耗时越长，不能认为显示预览后执行就无需再次读取。

### 7.2 检查两份产物与实际文件

以下核验只读，会重新读取全部已登记文件计算哈希，适合本批登记后的验收；日常登记脚本不会重新扫描旧 PDF。

```bash
python - <<'PY'
import hashlib
import json
from pathlib import Path

mapping = json.loads(Path('configs/pdf_files.json').read_text(encoding='utf-8'))
manifest = Path('data/source_manifest.jsonl')
records = [json.loads(line) for line in manifest.read_text(encoding='utf-8').splitlines() if line.strip()]
assert len(records) == len(mapping)
assert {record['doc_id'] for record in records} == set(mapping)
hashes = set()
for record in records:
    path = manifest.parent / record['raw_path']
    assert path == Path('data/raw') / mapping[record['doc_id']]
    with path.open('rb') as source:
        digest = hashlib.file_digest(source, 'sha256').hexdigest()
    assert digest == record['sha256'], record['doc_id']
    assert digest not in hashes, record['doc_id']
    hashes.add(digest)
print(f'PASS：{len(records)} 份记录的 ID、路径、实际哈希一致，无重复内容')
PY
```

此核验示例使用现有 Python 3.14 的 `hashlib.file_digest`，实现本身仍兼容项目声明的 Python 3.10。哈希一致只说明字节对应，不证明论文来源与解析内容正确。

### 7.3 更新当前已生成的清单

本批已完成刷新。以下适用于仍保留旧字段的记录，无需重新登记，先预览再刷新：

```bash

```

预览会显示“计划更新已有元数据：44 条”（假设仍为上一版未修改的 44 条记录）；正式执行后显示实际更新数。重复执行无新变化时应显示 0 条，清单不重写。不要删除路径配置，不要把 PDF 移回待登记目录。若之前已人工核实标题、年份或渠道，刷新保留这些已填写值。

预期以 `CIKM-2023-...` 开头的记录显示 `language: "en"`、`metadata.year: 2023`、`metadata.venue: "CIKM"`；`title` 中不再包含渠道和年份前缀，记录无 `downloaded_at` 或 `notes`。`doc_id`、路径、SHA-256 均保持原值。

### 7.4 PDF 解析后再补其余信息

作者、DOI、版本等先留空，待 PDF 解析后根据论文内容补齐。现有逐页解析器仅输出文字，不会自动提取这些文档元数据，也不会推进清单中的 `status`。后续实现结构解析时再接入补齐逻辑；当前无须提前查询来源网站。

人工补充时保持 `doc_id`、`raw_path` 与 `sha256` 不变，无需在 `pdf_files.json` 添加元数据。

后续先使用[PDF 解析教程](02-PDF解析.md)做代表论文基线检查，再按 [README](../../README.md#下一步结构解析再切块) 进入结构解析与切块。本功能不处理页码、图表或实验条件；这些仍由后续解析与证据模块保留。

本次文件名元数据扩展：上述 unittest 命令 **21 项通过**，新增对标题内连字符、arXiv、Unknown、非规范文件名的解析检查，以及旧清单预览无副作用、无需读取 PDF、保留已填写字段、刷新幂等与写入失败恢复的检查。此外在临时目录通过 CLI 新登记、旧记录刷新预览、正式刷新与重复刷新演练，路径配置修改时间和已有哈希均保持不变。对正式清单只读构建刷新计划：44 条可更新、待登记 PDF 为 0，44 条均可拆出标题、年份和渠道；两份正式文件原字节未变。正式清单的写入刷新留给用户运行。

隔离演练的临时目录已由上下文管理器清理。回归测试使用占位字节验证文件流程；不能将其解释为 PDF 解析质量测试。

## 9. 失败处理、重跑与恢复

|现象|原因与检查|处理与成功标志|
|---|---|---|
|预览显示 0 份|文件不在准确的 `raw/unregistered/` 或扩展名不是 PDF|核对路径和扩展名；文件不必移回 raw 根目录；正确放入后预览列出计划|
|重复内容（SHA-256）|相同字节使用不同文件名或已经收录|人工核对版本，将重复候选保存在本次待登记目录之外，不自动删除；重新预览无冲突|
|ID/目标路径冲突|同名论文、大小写冲突或 registered 已存在目标|确认原有文件来源；不同版本须独立 ID，不覆盖目标文件|
|配置与来源清单不一致|只删除了一份产物、手工改 ID/路径或中断|对照两份产物和文件，恢复匹配状态；不要只删除另一份来掩盖问题|
|哈希无效或 JSON 解析失败|人工编辑破坏格式或用了占位哈希|恢复正确 JSONL 与实际哈希；一行一个对象，禁止行间逗号和重复键|
|PDF 在预检后发生变化|登记期间有人改写文件|停止修改，核对本批已移回待登记目录，再重新运行预览|
|清单或配置在预检后变化|登记期间编辑了产物|本次在移动前中止；保存好编辑结果，重新规划|
|普通移动/写入失败|权限、磁盘或目标冲突|先检查报错和本批文件是否已恢复；修复原因后重试；首次登记失败不应留下半套产物|
|部分产物未能恢复|恢复过程本身失败|按异常列出的路径人工核对，不盲目继续登记；保留两份产物和 PDF 的现状副本再处理|

强制中断后先暂停登记，逐项检查：已写入的 ID 是否同时出现在两份产物、实际 PDF 是否在配置对应目标、记录哈希是否匹配。若只有一份产物提交，应从**同一登记前备份**恢复两份产物，再将本次未登记成功的 PDF 放回待登记目录；没有匹配备份时人工逐条核对，不能仅恢复旧 JSON。

脚本不自动生成持久备份或断点恢复日志。后续批次需要备份时，同时复制配置与来源清单；旧 `data/maintenance/` 下只备份了历史路径配置的资料不足以单独恢复新流程。操作成功后创建的空目标目录可能在失败后保留，不影响重新预览；不会为了清理目录删除文件。

## 10. 技术收获与后续衔接

应能区分文件字节标识、文档 ID 和论文版本：SHA-256 判断相同内容，ID 关联本地处理产物，版本需要来源证据。路径映射保证解析器仍能找到 PDF；来源清单为后续资料追溯提供数据，但不能代替人工核对。

本次实现和隔离验证已完成，用户已完成原统一登记；元数据刷新及名称规范化也已完成；名称修复的实际验证见[第 5 篇教程](05-PDF名称规范化与关联迁移.md)。下一阶段在代表论文上验证结构解析，保留原始物理页码和实验限定，再生成证据块；当前工作顺序统一见 [README](../../README.md)。
